# v0.10.x commit and recovery logic in the bounded model (2026-11-20)

Question (T1 in `research/drafts/v0101-paper-changes.md`): v0.10.x can put **two or more windows of one
source unit** in a cycle (rebuild #626; rotation/truncation; from #824 a size overflow). The submitted paper's
Theorem 1 assumed at most one pending batch per unit per cycle, and its model found the protocol unsafe at
B = 2. Does the v0.10.x ordering rule with **per-cycle hold-back** keep source-progress safety (I2) at B ≥ 2,
and which rules and assumptions are necessary?

Variant `v010` in `model/vtop_model.py` encodes the v0.10.1 code (44f6619), read for the paper study at the
lines cited in the variant's docstring and in `v0101-changes.md` §11–12. The hold-back block is byte-identical
on main after #824 (5623428), so the result also covers the planned v0.10.2. The v070/v060 code paths are
untouched: `--sweep` reproduces the 2026-11-11 output line for line (checked by diff).

Reproduce: `python3 model/vtop_model.py --sweep010` (≈ 50 s) and `--sweep010 --no-monotone`.
Raw output: `20261120-v010-sweep.{txt,json}`, `20261120-v010-sweep-nonmonotone.{txt,json}`,
`20261120-v010-sweep-resume-newest.{txt,json}` (`--resume-newest`).

## Answer, within these bounds

1. **Safe at B = 2 and B = 3 with hold-back.** v0.10.x keeps I2 with two and three windows of a unit per
   cycle, under failures, crashes, ledger-tail loss and storage mutation, up to 2,356,152 states.
2. **Hold-back is necessary at B ≥ 2 and not at B = 1.** Without it (`v010-nohold`) the B = 2 configurations
   violate I2 at the first failure, as v0.7.0's logic did; at B = 1 it changes nothing.
3. **The replayable-source assumption is necessary.** One refused hand-back (k = 1) violates I2 at B = 1 and
   B = 2: a later cycle's window commits past the range that could not be re-read. The engine counts and logs
   this (`vtop_source_replay_refused_total`, alert `VtopSourceReplayRefused`) but does not prevent it
   (confirmed by the engine maintainer, 2026-11-20). The paper already states it (Assumption *Replayability*, `asm:replay`); the model now shows it is necessary.
4. **No stalls** (confirmed monotone in-process; also with Kafka's newest-row resume). v0.7.0 left a range uncommitted until restart when its source commit failed (stalled up
   to 6,747 states); v0.10.x retries it in a later pass (#624) and settles held rows. 
5. **Duplicates.** With stable object keys, failures and crashes alone create no duplicate object
   (max dup 0, against 1–2 in v0.7.0); duplicates arise only when a stored object was damaged and the
   replay fell back to a per-attempt key (max 4 at N = 4 with one mutation and two failures).
6. **D2 (commit over damaged evidence) = 0**, against up to 3,576 states in v0.7.0 (also with newest-row resume).

## Robustness: the committed point not monotone (`--no-monotone`)

The model takes the committed point as monotone per unit. Without that assumption: **safety still holds in every
configuration** (up to 2,557,887 states), the ablation and refusal results are unchanged, but stalls return (up to
19,819 states) and D2 returns (up to 2,705), because a later pass's commit of a lower VERIFIED range lowers the point.

**Engine maintainer's answer (2026-11-20): monotone within a process in all three adapters.** A late commit of a
lower range is reported as success (the row becomes SOURCE_COMMITTED) and skipped at the source: file
`commit_progress` (file_source.rs:3818-3842, `committed_byte >= end_byte` with the file proven), Kafka frontier
skip `commit_at <= known_committed` and max-ed frontier (kafka_source.rs:3470-3499), spool (syslog_spool_source.rs:807,
:823, replay clamp :895). So findings 4 and 6 hold for a running engine.

**Across a restart, Kafka resumes from the newest-created committed row, not the max end** (#617;
`committed_kafka_offsets`, sqlite_store.rs:520-545, `created_at DESC, batch_id DESC`). Modelled with
`--resume-newest` (`20261120-v010-sweep-resume-newest.{txt,json}`): **safety holds, no stall, D2 = 0** in every
configuration (to 2,263,247 states); the hold-back ablation and refusal rows are unchanged. The model does reach a
state where the newest-created committed row has a lower end than an older one (N=3, B=1, 1 failure, 2 crashes,
1 mutation: a source commit fails, the object is damaged while down, recovery replays the lower range as a new row
that commits, then the older higher row commits at the next recovery). A further restart then resumes below the
true committed point and re-archives the higher range: **a duplicate, not a loss.** Reported to the maintainer
(MAX(end) per partition would make it monotone). **Engine follow-up:** PR #844 tried MAX(end) and it opens a
loss on topic deletion and recreation (offsets restart at 0 under the old incarnation's higher end), so v0.10.2 keeps
newest-row resume; a fix needs the topic id in the marker. Modelling topic recreation is future work: the expected
results are newest-row = duplicates, MAX = loss unless incarnations are distinguished.

## Not modelled

One unit only (no cross-unit or rotation inode change); held ranges whose replay decision could not be
recorded (#639) and rewind lowering above them (#782); a power loss that drops more than the newest ledger
write (the engine's faithful emulation truncates the WAL to the last FULL write; the model drops at most the
newest non-FULL write); Object Lock; read-order commit at B ≥ 2 was not ablated for v010.

§V's "read-order commit not shown necessary at B = 1" stays and gains "hold-back necessary at B = 2".
